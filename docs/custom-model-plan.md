# 自制 Live2D 模型方案（设计稿，未执行）

> 目标：摆脱 hiyori 的授权限制（禁改设计 / AI 用途待确认），为 Ayan 制造一个
> **完全自有、可商用、完全适配桌宠** 的 Live2D 模型。
> 调研时间：2026-10-15。本文件只做方案，不含任何已执行动作。

## 0. 背景与动机

- hiyori 官方样本数据对个人可商用，但两条绳索：**禁改角色设计** + **AI 聊天用途
  可能被官方归类为"可扩展性 APP"（需逐作品签约，邮件待发）**。
- 上 Steam 商业发行后这两条都会被放大。自制模型一次性解决：设计权、改动权、
  发行权全归项目（只剩 Cubism SDK 本身的许可，反而更宽松）。
- 已有架构红利：`e0fbc28` profiles 档案化后，**加模型 = 建档案 + 注册一行**，
  runtime 侧适配成本已压到最低。

## 1. Live2D 模型的四道工序（与能力对照）

| 工序 | 内容 | 纯人工基准 | 我方能力（2026 工具链） |
|---|---|---|---|
| ① 角色设计 + 立绘 | 人设、三视图、定稿立绘 | 画师 3~7 天 | ✅ ImageGen 迭代概念图可行 |
| ② 分层 PSD | 眼白/瞳孔/睫毛分层、张嘴差分、前后发分离、**被遮挡区域补全**，几十层 | 画师 1~2 周 | ✅ 已过关。See-Through 5050★；Bunraku（2026 论文）证明可行但**未放代码/权重**（见 §9.7） |
| ③ 绑定 rigging | 网格、变形器、参数、物理 | 绑定师 1~4 周 | ✅ `psd2live`（开源）：分层 PSD → 自动 .moc3/.cmo3，可回官方编辑器精修 |
| ④ runtime 适配 | 档案、情绪 16 字段、摸头、走路 | — | ✅ 本行，估 4~5 工作日（详见 §4） |

## 2. 三条路线

### 路线 A：全自动（我 + AI 工具链，零人工外购）
- 流程：ImageGen 设计定稿 → AI 分层（Bunraku 式/prompt 拆层）→ psd2live 自动绑定 → 档案适配。
- 时间：**1~2 周 demo**。
- 判死刑的两点：
  1. AI 分层的遮挡补全质量不稳（眼皮后的瞳孔、发丝后的肩），绑定撕裂风险高；
     ⬇️ 2026-10-28：See-Through 显著抬高（§9.2）。
  2. ~~**自动绑定工具链全部是 VTuber 半身向，没有人给"腿"做优化** —— 桌宠刚需的
     全身漫步/走路循环做不出来。~~
     🔴 **2026-10-28 反转**：降档后（§11）我们**只要半身**，于是「半身向」从缺点变成**对口**；
     且「漫步靠腿」本身是误判（§11.2）。**此条不再成立，路线 A 不再是死刑。**
- 结论：~~只配当 PoC~~ → **降档后（L0/L1）可作为交付路线**（§11.5）。

### 路线 B：半自动（推荐）✅
- 流程：我出设计定稿 → **画师做分层 PSD（唯一外购人工，约 1~2 周）** →
  psd2live 自动绑定 → 我做绑定精修 + runtime 适配。
- 时间：**2~3 周日历时间**（画师与我并行度高）。
- 成本：画师分层 PSD 行情约 ¥2000~6000（按层数与差分复杂度）。
- 品质：接近商用——分层是人工的（质量可控），绑定自动化后人工精修兜底。

### 路线 C：传统全委托
- 画师 + 绑定师全外包：1~3 个月、数万元。放弃设计参与权，不推荐。

## 3. 设计规格（路线 B 的输入，也是给画师的委托书骨架）

**硬性需求（来自现有系统，缺一个 runtime 适配就多一天）：**

| 项 | 规格 | 为什么 |
|---|---|---|
| 形态 | **胸像 / 半身即可，腿为可选**（原写「全身含完整腿脚」，**2026-10-28 降档，见 §11.2**）；仍需真人比例、不要二头身 Q 版 | 漫步 = 窗口位移（Walk 动作是我们自制的增强，非必需）；sjmsltx 实测：Q 版脸太小不适合 Live2D 表情（见 open-source-reference.md 11.1-A3） |
| 基础差分 | 眼开/闭/半闭、口开/闭/半开、视线四方 | EMO_SPEED 错峰插值 + 口型 |

| 部件命名 | 按 psd2live 命名表（它的自动识别靠这个） | 自动绑定通过率 |

**设计自由度：**
- 风格与 hiyori 元气少女/ Miara 御姐错位（建议"第三种气质"，比如冷静系/治愈系），

## 9. 2026-10-28 复核：四段自制链路（全部经 GitHub API 核实存在）

用户提出的一条链路：**NovelAI 立绘 → See-Through 拆层 → psd2live 绑骨 → pixi-live2d-display 渲染**。

| 环节 | 仓库 / 产品 | 许可 | 判定 |
|---|---|---|---|
| 立绘 | NovelAI（闭源 SaaS，$10/月起） | 官方 FAQ：不主张生成物所有权、无商用档位限制 | ⚠️ 可用，见 §9.5 |
| 拆层 | `shitagaki-lab/see-through` 5050★ Python | **Apache-2.0** | ✅ **本轮唯一新增价值** |
| 绑骨 | `tsunehimatoi/psd2live` 767★ Kotlin（3 天内仍有提交） | **GPL-3.0** | ✅ 只跑不分发即可 |
| 渲染 | `@naari3/pixi-live2d-display` | MIT | ✅ **就是我们在用的** |

### 9.1 渲染格不用动 —— 已经是它了

`package.json` 已是 `@naari3/pixi-live2d-display@^1.2.5` + `pixi.js@^8.22.0`，
`src/renderer/pet.js:2` import 的是 `@naari3/pixi-live2d-display/cubism5`。
它是 pixi v8 + Cubism 5 的维护分支（npm peer `pixi.js ^8.0.0`，MIT；
上游 `guansss/pixi-live2d-display` 1515★ 是 Cubism 4 / pixi v7 时代那条线）。
→ 自制模型只要**导出 Cubism 5.x**，就直接落进现有 runtime，渲染侧零改动。

### 9.2 See-Through 补的正是 §1 表里标红的「最弱环」

SIGGRAPH 2026 conditional accepted，单图 → 23~24 层 PSD，自动补遮挡（发后的额头、衣下的身体）、
左右件自动分侧、头发按深度聚类分前后。§2 路线 A「判死刑」的第一点（AI 分层质量不稳）被显著抬高。

⚠️ 作者自己明说：**不是 Image-to-Live2D**，只做拆层 + 遮挡补全，绑定与艺术意图都不在内。
它把「手动拆 1~2 天」压到「100 秒 + 人工修」，不是压到零。

### 9.3 🔴 两个工具之间有官方衔接点（本轮最有用的发现）

psd2live 的 `docs/en/spec/PSD_LAYER_SPEC.md` 原文写着：由程序拆出来的部件
（原文即 `such as AI layer decomposition`）**可以不要 PSD**，走 **layout manifest**
—— 一个 JSON（或根目录含它的 zip），列出每层的图片、画布矩形、堆叠顺序、组、标签、变体；
无标签的层走命名规则兜底。

而且它的分类器**同时认英文 / 中文 / 日文 / 韩文层名**，`front hair / back hair / face /
iris / eyebrow / eyewhite / eyelash / mouth / tooth-t / tooth-b / tongue / neck / topwear /
handwear / bottomwear / legwear / footwear / tail / wings / objects` 全在表里
—— 与 See-Through 输出的 24 层**高度重合**。

→ **中间不需要人工重命名那一层**，缝隙比预想小得多。这是把两件事接起来的正路。

### 9.4 两条硬伤（⚠️ 2026-10-28 降档后**均已降级**，见 §11）

1. **嘴必须给「全开」素材。** psd2live 原文：
   `Geometry cannot reconstruct an unseen mouth interior from closed-mouth pixels`。
   ⬇️ **降档订正**：规范紧接着写 `Supply the mouth fully open, **either as one image**
   or with separate upper teeth, lower teeth and tongue` —— **一张张嘴图就够，五件分件不是必需**；
   且「生成张嘴差分」≠「从闭嘴重建」，前者可解。剩下仅是幅度问题 → `mouthOpenMax` 夹取（§11.3）。
2. **全身含腿存疑。** See-Through 的 24 层里只有「腿饰 / 鞋子」，**没有腿的肉身层**。
   ⬇️ **降档订正**：**「漫步全靠腿」是我上一轮的误判** —— 漫步是窗口位移，Walk 动作是我们
   自制的增强（§11.2）。腿由此从「硬伤」降为「可选增强」，半身即可交付。

### 9.5 许可

- **psd2live 是 GPL-3.0**：copyleft 义务只在「分发」时触发 —— 我们只是**跑它**产 `.moc3`，
  不并入本 app，不触发。🔴 红线：**绝不能把它的代码打进 Ayan.exe**，也不许 npm 进依赖。
- **NovelAI**：官方不主张生成物所有权、允许商用（不设商用档位），但**不做 IP 兜底
  （no indemnification）**，且纯 AI 生成缺 human authorship → 拿到的是「使用权」不是「版权」。
  相比 hiyori 的「禁改设计」，是换了一种风险，不是消灭风险。
- Cubism 5.3 的混合模式导出到旧 runtime 会降级为 Add 并在 loss report 里写明 ——
  我们 runtime 是 cubism5 构建，导出就选 **Cubism 5**。
- 自制模型照样走规矩 13：**素材不进仓库**，放 Release 的 `models.zip`。

### 9.7 「全靠 AI」到底差在哪（2026-10-28 二次检索：Bunraku 现状 + 自研 moc3 编译器）

回答「AI 现在能不能端到端出可交付模型」——**不能**，卡点不在算力，已逐条核实：

**① Bunraku（清华/SparcAI，arXiv 2607.27348，2026-07）是第一个端到端系统，但拿不到。**
- `SparcAI-Inc/Bunraku`：**41★、0 fork、仓库里只有一个 `readme.md`（722 B）、1 次提交（2026-07-31）、
  0 release、无 license**。即 **代码与权重都没放**。
- 项目页只有 WebGL 演示**预生成角色**（可拖 slider、指针注视、展开图层栈），
  **没有「上传自己的图跑一遍」的入口**；数据集/商用/学术合作一律**发邮件**。
- 已放出的部分：Live2D-Bench（120 组 PSD）+ 8,884 模型语料（需邮件索取）。
- 它自己的指标：Stage 2 每顶点**方向**余弦 0.768（中位 0.828，50 个留出角色），
  对照「逐层独立预测」0.693。🔴 **这是方向、不是幅度**——作者自述「小动作容易做过、
  大转动容易不足」，主指标只在 50 个角色上报告。
- 🔴 **最反直觉的一条**：网络放大 112×（5.1M → 571.6M）精度**毫无提升**，十亿参数甚至发散。
  → 瓶颈是**任务歧义与跨层协调**，不是模型容量。也就是说：等下一代更大的模型**救不了这一格**。

**② 真能跑通端到端的只有「自研 moc3 编译器」那一类：`mw2wbyys6t-sudo/live2d-auto-pipeline`。**
- Apache-2.0、13★、100 MB、2026-10-26 仍在提交；`moc3_pipeline.py` 64 KB + `moc3_model.py` 48 KB，
  含网格/骨骼/变形器/28 表情参数/物理；README 自述通过官方 Cubism Native Core 逐像素验收
  （504 passed / 96 skipped）。
- ⚠️ **但「能被官方内核加载」是二值门，太容易过**，不等于美术质量达标 —— README §已知局限第 4 条
  作者自己写：「**可用但粗糙**的起点，自动绑定无法替代专业 Live2D 技术师的手动精调」。
- 对本仓的三处不兼容：**导出 Cubism 4**（我们是 Cubism 5 runtime）· 默认分层是 **K-means 颜色聚类**
  （语义分层要下 2 GB SAM 权重）· 自带 `drivers/desktop_pet` 但自标「**未实机验证**」。

**③ 结论：四道工序里 AI 的成色不均，短板恰好是桌宠最吃的那两格。**

| 工序 | AI 现状 | 判定 |
|---|---|---|
| ① 立绘 | 过剩 | ✅ |
| ② 分层 + 补遮挡 | See-Through 5050★ / Bunraku Stage1 | ✅ **已过关** |
| ③ 网格 + 绑骨 | 规则式（psd2live）要规范层名 + 全开嘴素材；学习式（Bunraku）**拿不到** | ⚠️ 半程 |
| ④ 表情设计 / 物理手感 / 口型 | 需**艺术意图**，不可从单图推断 | ❌ **必须人工** |

→ **三处硬卡点，都不可靠「再等等模型变强」解决**：
（a）**口腔**：psd2live 原文「无法从闭嘴像素重建未见的口腔内部」，而 NovelAI/生图几乎必闭嘴；
（b）**腿**：See-Through 24 层只有腿饰/鞋子，无腿肉身层 ~~而漫步/回位全靠腿~~
    🔴 **订正**：漫步 = 窗口位移，腿非必需（§11.2），降档后半身即可 → **此条不再卡人**；
（c）**表情与物理**：我们 8 情绪 × 16 字段的错峰插值是*设计*不是*重建*；physics3.json 的摆锤参数同理。

**④ 值得单独记的一条（Bunraku 独有）**：它的网格**只由 alpha 通道导出** → 纹理与运动彻底解耦，
**换装只重新纹理化，网格与预测动画可 byte-for-byte 复用**。这条正好对口我们「多套衣服/季节皮肤」
的潜在需求，且不依赖它放权重——只要将来有同类实现就能用。**记入 backlog 候选。**

## 10. 不走 Live2D 还有哪些路（2026-10-28 检索，全部经 npm / GitHub API 核实）

### 10.1 先明确「要绕开的是什么」

§9.7 的三条硬伤里，**口腔与腿是同一类问题：原画里根本不存在的信息**。
→ 判据：**任何纯 2D 方案都绕不开它们**；只有带骨架的 3D 从一开始就有这份几何。
（表情/物理是第三类，属艺术意图，换任何路线都要人工。）

### 10.2 四条候选逐条核实

| 路线 | runtime / 许可 | 治口腔 | 治腿 | 判定 |
|---|---|---|---|---|

### 10.3 VRM 为什么真能绕开（规范原文核实，非印象）

来源 `vrm-c/vrm-specification`（345★）`specification/VRMC_vrm-1.0/expressions.md`：

- **口型是规范一级公民**：`Lip Sync Procedural` 预设 **aa / ih / ou / ee / oh**（原文表，注：ih=i、ou=u、ee=eh）；
  眨眼 `blink / blinkLeft / blinkRight`；情绪 `happy / angry / sad / relaxed / surprised`；视线 `lookUp/Down/Left/Right`。
  ⚠️ 原文第 141 行 **「All preset expressions are optional」** → 具体模型可能缺项，**运行时必须探测不能假设**。
- **物理是规范自带**：`VRMC_springBone-1.0`（含 extended_collider / limit 扩展）→ 头发、衣服摆动**不用自己调摆锤参数**（对比我们 hiyori 物理的教训）。
- **全身有骨架** → 走路可用现成动画（`VRMC_vrm_animation-1.0` / fbx），**腿的问题从根上消失**；转头、侧脸同理（Live2D 转头 >30° 就崩）。

→ 我们 TTS 的口型、`verify-lip` 那套正弦驱动，**在 VRM 上是直接对接 blendshape，不需要画口腔**。

### 10.4 但代价要算清楚（别只看好处）

- **现有资产几乎全废**：`params.js` 的 16 字段 × 8 情绪、`EMO_SPEED` 错峰插值、`profiles/*.js` 模型档案、
  `measureHead()` 扫像素、`headTopY` 摸头、大半 `verify-*.js` 断言——全部建立在 2D Cubism 参数语义上。
- 🔴 **与既有踩坑正面冲突**：`antialias:false` 别加回来、内存已 ≈657MB、低配降帧三档——3D 全踩在这些红线上。
- 透明无边框窗 + 3D：透明边缘锯齿、与底座窄卡片（147 宽）的叠加关系要重做。
- 风格：MToon 材质可接近赛璐璐，但**不再是「画师原画那一笔」**；模型体积常见 10–50MB。
- ⚠️ 待复核（聚合站引官方，未亲自核）：Live2D 免费档上限 100 ArtMesh / 30 参数 / 50 deformers / 单张 2048 纹理，
  免费商用限年销售额 <1000 万日元的个人与小微企业；**全身模型 100 ArtMesh 偏紧**——若属实会影响自制路线。

### 10.5 许可：比 NovelAI 干净得多

VRoid Studio Guidelines：pixiv 保留**预置件**版权，但授权允许**商用、修改、再分发**（按各预置件条款；
部分 sample 为 **CC0**）。相比 NovelAI「不主张所有权但**不做 IP 兜底**」，这是清晰得多的授权链。
🔴 **红线**：Guidelines 明写**不能做「能生成/输出 3D 模型的应用」**——我们只是加载播放，**不触发**，但别越线。
⚠️ VRoid Hub 上别人的模型是 **per-model 条件**（存在 `Corporate use: Do not allow` 的）→ **自己用 VRoid Studio 捏一个最干净**。

### 10.6 判决

1. **换 Spine：排除**（花钱不治硬伤）。
2. **换 VRM：唯一真解法，但它是「第二世代」工程，体量大于 Tauri 迁壳。**
   🔴 **必须与 `docs/tauri-migration.md` 合并决策**：若将来本就要迁壳，就**把渲染后端一起换**，
   一次重写解决两件事；现在分开做 = 重写两次。
3. **短期仍走 Live2D 路线 B**，AI 只省掉分层这一步（See-Through）。
   🔑 **口腔改走「生成张嘴差分」而不是「从闭嘴重建」**——生成 ≠ 重建，这条**是可解的**，
   委托书里明写「闭嘴 / 半开 / 全开三态 + 口腔内三件分件」即可。
4. **低成本预研（半天，可随时插队）**：VRoid 捏一个 → three-vrm → Electron 透明窗，
   只验三件事：**透明边缘** / **内存增量** / **口型 blendshape 能否接现有 TTS**。三条都过才值得排期。

**三个选项**

- **A 并存（现状）**：零成本，代价是两套配置、两套打包与发版、两套用户心智。
- **B 在 Unity 里用 C# 重写上层**：3D README 已判「别复用 2D 主进程代码（Unity 单进程，9176 行 Node

### 11.1 卡点重估：两条降级，一条维持

### 11.2 「腿是刚需」是我上一轮的误判 —— 现在证伪

上一轮我写「漫步 / 回位 / 贴边全靠腿」，并把 §3 硬性需求第一条定成「**全身含腿**」。
**读代码后这个判断站不住**：

- `motion.js` 的漫步是 **`WALK_SPEED = 190 px/s` 的窗口位移**，`walkDuration(dist)` 按距离算时长；
- 播的 `Walk` 动作是**我们自己用 `tools/make-motions.js` 做的**（`hiyori.js:70` 注释原文：
  `Drag / Walk：本项目手写的（tools/make-motions.js）`），不是模型自带的；
- `motion.js:288` 注释原文：**「不动（只挪窗口）所以看不出来」** —— 说明
  「只挪窗口」本来就是漫步的一种正常工作模式，Walk 动作是后加的增强；
- 规矩 24：`motion.wander` **默认关闭**。

→ **半身模型完全可用**：不播 Walk，漫步退化为整体平移。
代价只有一条：溜达的时候她不迈腿。而且 3D 侧（`ayan-3d`）M7 入场行走 + M9 BVH 重定向
已经把「腿和走路」这条赛道赢了 —— 2D 再为腿付出全身成本不划算。

**🔑 顺带一个反转**：§2 路线 A 判死刑的第 2 点写的是「自动绑定工具链**全是 VTuber 半身向**，
没人为腿做优化」。降档之后我们**只要半身** —— 于是这个「缺点」变成了**对口**。
psd2live / See-Through 整条生态都是围着半身长出来的，我们正好落在它的甜区里。
（这条也从侧面说明：上一轮的严格标准不是技术事实，是我自己加的。）

**§3 硬性需求第一条据此改写**：形态从「全身正立、含完整腿脚」改为「**胸像及以上即可，腿为可选**」。

### 11.3 口腔：规范比我说得宽松，且只需一个参数

- **分件不是必需**（上面原文）。只要给一张「全开」的张嘴图（`MOUTH_OPEN` 层名 `mouth open` / `张嘴`），
  就能生成开合。规范还给了防穿帮的正解：`口腔底` **画得比嘴能张到的极限更大**，
  由 `口腔` 层裁剪 —— 原文：`so nothing behind the mouth shows in any mouth shape`。
- **口型只写一个参数**：`pet.js` 三条分支全部是 `setParam(P.MOUTH_OPEN, mouthLevel)`，
  映射 `ParamMouthOpenY`（`hiyori.js` param 表）。真包络 `lipEnv()` 与正弦回退都走这一个口。
- 正弦分支当前幅度：`(sin * 0.5 + 0.5) * 0.7 + 0.15` → **0.15 ~ 0.85**，确实偏大。
  → **降档解法：档案声明 `mouthOpenMax`（建议 0.35），写参前夹**。一个参数的事。
- 「从闭嘴重建口腔」不可能；但**「生成一张张嘴差分」是可解的**（§10.6 第 3 条已记）——
  NovelAI / ImageGen 直接在 prompt 里要 `open mouth, teeth visible` 出一张即可，
  **生成 ≠ 重建**，这条不受限。

### 11.4 8×16 是 verify 的断言，不是引擎的限制

- `hiyori.js:7` 注释原文：**「emotion 8 情绪 × N 字段（N 不必是 16 —— 引擎按字段集遍历）」**
  → 引擎天然支持少字段档案。
- 但 `verify-expressive.js` 有两条**硬编码断言**：
  - `:66` `ok(names.length === 8, '情绪数 = 8')`
  - `:73` `ok(base.length === 16, '字段数 = 16')`
- 情绪名与 `[emo:xxx]` 协议强绑定：`config.js:318`
  `EMOTION_TAGS = ['calm','happy','smile','think','shy','serious','surprised','sleepy']`。

→ **降档真正的成本在这里，而且只有三处小改**（见 §11.6）。

### 11.5 三档定义

| | **L0 够用档**（新默认） | **L1 舒适档** | **L2 冻结**（原 §3 规格） |
|---|---|---|---|
| 形态 | **胸像 / 半身** | 半身或全身 | 全身含腿 |
| 腿 | ❌ 无（漫步=整体平移） | ⚠️ 可选 | ✅ 必含 |
| 情绪 | **4 个**（calm/happy/shy/sleepy） | 6 个 | 8 个（全套） |
| 字段 | **8~10 个** | 12~16 | 16 |
| 嘴 | 一张张嘴图 + `口腔底`，`mouthOpenMax 0.35` | 张嘴差分 + 牙齿单件 | 口腔五件分件 |
| 物理 | 只保留呼吸 + 头发基础 | + 身体摆动 | 全量 |
| 产出方式 | **全 AI 可达**：生图 → See-Through → manifest → psd2live | AI + 少量人工修 | 画师分层 PSD（路线 B） |
| 适配工时 | **1~1.5 天** | 2~3 天 | 4~5 天 |

**判决：L0 作为 PoC 目标，L1 作为交付目标，L2 冻结**（等 3D/2D 合流后视情况解冻）。

### 11.6 降档需要的三处代码改动（都很小，且都不动 hiyori / whale 行为）

1. **`verify-expressive.js:66/:73`**：8 / 16 两条硬断言 → **改为从档案自证**
   （断言规则一条不减：情绪间键集必须相同、`emoSpeed` 键集 = 字段集、`param` 里必须有对应 ID）。
   期望值来自档案声明，不再写死常数 —— 也顺带满足规矩 9「同一数值只有一处定义」。
2. **未知情绪回退**：档案声明 `emotionAlias`（例：`smile→happy`、`think→serious`、
   `surprised→happy`），8 个协议标签**一个都不删**，`[emo:xxx]` 协议不动、llm prompt 不动，
   命中缺失情绪时映射到近似档。**必须显式回退，不能静默停在旧值**（这正是
   `hiyori.js:13` 注释警告的那个「眉毛卡住」故障）。
3. **`mouthOpenMax`**：档案新增一个字段，`pet.js` 三条 `setParam(P.MOUTH_OPEN, …)` 前统一夹取，
   默认 1.0（现有两个模型行为逐字节不变）。

> 三条都符合规矩 4「新增能力一律做配置开关」与「改一半」禁令的反面：改就改全套。

### 11.7 降档后的 PoC 验收标准（替换 §9.6 那两条）

原标准「口腔开合能不能动 + 腿在不在，过不了就放弃」**作废**。新标准三条，全是「够用」级：

1. `ParamMouthOpenY` 存在，0→1 能张开，且**张到 0.35 时不露空白**（口腔底够大即过）；
2. 至少 **4 个情绪**可切换，且**切 A→B 时全部字段跟着走**（用 `verify-expressive` 的键集断言跑）；
3. **半身几何标定过得去**：`headTopY` 量得出（摸头 A-B-C 依赖它）、底座不压人（规矩 14）、
   两档窗口宽度复验（规矩 20）。

**「腿在不在」不再是否决项** —— 不满足只是停在 L0，不判死刑。

### 11.8 与 3D 的关系（不变，反而更顺）

§10.7 的结论不受影响：形体赛道 3D 已赢。
降档让 2D 的定位更清楚 —— **轻量 / 低内存 / 可快速换皮的备选身**，
不再跟 3D 比形体。这也意味着 §11.5 的 L2 没有排期理由。
